#  Задание 1. Анализ и планирование

## 1. Описание функциональности монолитного приложения

**Управление отоплением:**
- Система поддерживает добавление, обновления и удаление систем отопления;
- Пользователи могут изменить желаемое значение температуры;

**Мониторинг температуры:**
- Пользователи могут получить значение текущей температуры (для всех счётчиков, по ID и по локации);


## 2. Анализ архитектуры монолитного приложения

- **Язык программирования**: Go

- **База данных**: Postgres

- **Архитектура**: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.

- **Взаимодействие**: Синхронное, по RestAPI на базе протокола HTTP.

- **Масштабируемость**: Горизонтальная масштабируемость возможна, но потребует поднять всё приложение полностью. Нет возможность масштабировать отдельные части приложения.

- **Развёртывание**: Обновление приложения требует полной остановки всего приложения. Отсюда следует низкая отказоустойчивость.

- **Расширяемость**: В дизайн приложения (код, API) не заложена возможность легко расширять приложение.


## 3. Определение доменов и границы контекстов

* **Домен: управления системами отопления**
    * Поддомен: управление системой отопление
        * Контекст: настройка системы отопления (CUD)
        * Контекст: настройка температуры
    * Поддомен: мониторинг систем отопления
        * Контекст: получение значения температуры


## **4. Проблемы монолитного решения**

- **Расширяемость**: В дизайн приложения (Код, API) не заложена возможность легко расширять приложение. Потому будет сложно интегрировать устройства новых типов (ворота, наблюдение, свет).
- **Безопасность**: В систему не заложена безопасность и ролевая модель: кто угодно может читать что угодно по id.
- **Масштабируемость**: Например, сложно отделить мониторинг от добавления новых систем отопления, хотя ими пользуются разные акторы и их количество и создаваемая нагрузка может различаться.
- **Надежность**: Существует единые точки отказа: БД, приложение. 
- **Развёртывание**: Нет возможности развернуть часть системы отдельно.

# Задание 3. Разработка ER-диаграммы

## Сущности
* Пользователь (User)
* Дом (Home)
* Устройство (Device)
* Телеметрия (TelemetryData)

## Атрибуты

### Сущность "Пользователь"
* Email - идентификатор пользователя в системе
* Name - имя пользователя
* Password - пароль пользователя
* CreatedAt - дата создания

### Сущность "Дом"
* HomeId - идентификатор дома в системе
* Address - адрес дома
* CreatedAt - дата создания

### Сущность "Устройство"
* DeviceId - идентификатор устойства в системе
* Name - название устройства
* DeviceType - тип устройства
* HomeId - дом, в которое добавлено устройство
* CreatedAt - дата создания

### Сущность "Телеметрия"
* TelemetryId - идентификатор телеметрии
* DeviceId - идентификатор устройства
* CreatedAt - дата создания
* Value - показание устройства

## Описание связей
* **Пользователь - Дом**: Многие ко многим. У одного пользователя может быть несколько домов, у одного дома может быть несколько пользователей.
* **Дом - Устройство**: Один ко многим. Один дом может содержать несколько устройств, и каждое устройство принадлежит только одному дому.
* **Устройство — Телеметрия**: Один ко многим. Одно устройство может генерировать множество записей телеметрии.
